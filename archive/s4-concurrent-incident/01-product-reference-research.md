# 阶段 4 · 产品参照调研

> 调研日期：2026-09-17  
> 项目声明：本项目基于抽象业务场景与模拟数据，用于展示产品流程判断能力；不代表作者曾在真实公司主导、上线或运营该产品。  
> 调研目标：为可点击 HTML Demo 提炼可复用的界面形态，不复制品牌外观，不把参照产品能力表述为本项目已实现能力。

## 1. 结论先行

本项目不应做成“左边聊天、右边空白”的通用 AI 助手，也不应做成只有指标卡的传统风控驾驶舱。建议采用三层结构：

1. **稳定的一级侧栏**区分“在线风控”与“AI 工作台”，避免 14 个界面混在同一层级。
2. **对话流作为任务编排画布**，在消息流内嵌执行计划、确认卡、进度、失败恢复和证据摘要；自然语言只是入口，可确认对象才是操作主体。
3. **右侧对象栏作为持久化锚点**，实时列出实验、任务组、证据链和报告，解决“说完之后到哪里找”的问题。

信息密度采用“结果优先、细节渐进”：首屏先看到任务状态与关键判断，表格、完整参数、证据步骤按需展开。状态不能只靠颜色表达，必须同时有文字、图标或形状。

## 2. 参照产品

### 2.1 LangGraph / LangSmith：对话、工具执行与可观测对象共存

**可核实事实**

- Agent Chat UI 支持实时对话、工具调用可视化、interrupt，以及 time-travel debugging / state forking；其交互对象不是纯文本消息，而是可呈现工具执行和中断的运行记录。[官方文档](https://docs.langchain.com/oss/javascript/langgraph/ui)
- LangSmith 将单次运行组织为 trace tree，并同时提供项目统计和 dashboard；明细、聚合和趋势处于不同层级。[官方文档](https://docs.langchain.com/langsmith/cost-tracking)
- LangGraph Studio 可在界面中检查图状态和 interrupt，说明“对话入口 + 执行状态面板”是一种成熟形态。[官方文档](https://docs.langchain.com/oss/javascript/langgraph/interrupts)

**可借鉴**

- 对话消息内直接显示工具/步骤状态，不把执行过程藏进一个旋转中的气泡。
- 将一次需求稳定映射为 thread / run / trace 等正式对象；本项目对应“实验 / 任务组 / 证据链 / 报告”。
- 中断必须成为一等状态：暂停后保留旧结果、显示等待动作和继续入口。

**不照搬**

- LangGraph 偏开发调试语境。本项目面向风险产品演示，首屏应使用业务对象和判断语言，隐藏 graph/node 等工程词汇。

### 2.2 Microsoft Sentinel：案件详情、时间线与证据在同一上下文内

**可核实事实**

- Sentinel 的案件详情页将基础信息保留在常驻左侧面板，其余区域用 Overview / Entities 等页签承载调查内容；证据、日志和实体可在案件上下文内打开，而非频繁跳页。[官方文档](https://learn.microsoft.com/en-us/azure/sentinel/investigate-incidents)
- Incident timeline 按时间组织 alerts 与 bookmarks，并支持筛选；调查图用于查看实体关系，但官方也指出图形调查会带来更多上下文切换。[官方文档](https://learn.microsoft.com/en-us/azure/sentinel/incident-investigation)

**可借鉴**

- 案件/任务的身份信息应保持可见，详情用抽屉、页签和折叠区渐进展开。
- 时间线适合证据链与任务执行轨迹；每一步显示时间、工具、状态、输入摘要和缺失原因。
- 对高风险操作采用明确动作区，并把“审批中 / 等待人工 / 已失败”做成常驻状态，而不是一次性 toast。

**不照搬**

- 关系图不应抢占主界面。阶段 4 的主线是“可讲的流程闭环”，证据图只在独立证据链页按需出现。

### 2.3 Stripe Radar：从风险概览下钻到人工复核与处置

**可核实事实**

- Radar 同时覆盖风险评分、规则、名单、实时监控、风险洞察和人工复核，形成“概览 → 具体支付 → 人工动作”的运营路径。[官方文档](https://docs.stripe.com/radar)
- Radar analytics center 先展示某一时间段的汇总与分布，再允许从表格行进入规则表现，体现“先结果、后归因明细”。[官方文档](https://docs.stripe.com/radar/analytics?locale=es-419&radar-dash=legacy)
- Review 场景会把 approve / cancel / capture 等动作并列呈现，并明确“批准复核不等于自动完成后续资金动作”，适合作为“确认动作与真正生效动作分离”的参照。[官方文档](https://docs.stripe.com/radar/reviews/auth-and-capture)

**可借鉴**

- 看板首层给出少量高价值指标，点击后进入同口径样本，不在看板直接编造归因。
- 规则、名单、风险洞察和人工复核使用一致的业务语言与状态标签。
- 把“生成包”和“在线侧确认生效”拆成两个动作，视觉上明确谁能做、目前走到哪一步。

**不照搬**

- Stripe 的对象主要围绕支付。本项目还要覆盖离线实验、Agent 版本与工具授权，导航需要额外的工作台域。

### 2.4 Datadog / Ant Design 可视化规范：高密度但不失序

**可核实事实**

- Ant Design 的可视化页面规范建议先摘要、再筛选、最后给细节，重要指标放在上方，并将同屏模块控制在 5–9 个以内。[官方规范](https://ant.design/docs/spec/visualization-page/)
- Ant Design 将表格用于结构化比较，将折叠用于渐进获取信息，并要求时间、状态和操作列尽量不换行。[官方规范](https://ant.design/docs/spec/data-display/)

**可借鉴**

- 主界面不堆满卡片：一个主任务区、一个轻量运行状态区、一个对象侧栏足够。
- 任务列表与案件样本用表格，执行轨迹用时间线，阶段总览才用指标卡；不同信息类型不强行卡片化。

## 3. 横向归纳

| 设计问题 | 成熟形态 | 本项目决策 |
|---|---|---|
| 导航怎么切 | 稳定侧栏承载一级域，页面内用页签/抽屉做上下文细分 | 一级分“在线风控 / AI 工作台”，二级直接列冻结界面；不做第三层常驻导航 |
| 信息密度怎么组织 | 摘要 → 筛选 → 明细；对象详情常用表格、时间线与侧栏 | 对话首屏只保留当前任务；对象历史移至左侧会话与右侧对象栏 |
| 对话与后台控件怎么共存 | 对话负责意图，卡片/表单负责确认，run/trace 负责留痕 | 自然语言提出需求；计划卡、确认卡和参数抽屉完成结构化操作 |
| 状态怎么表达 | 颜色 + 文本 + 图标；长时状态常驻，短反馈才用 toast | 执行中、审批中、灰度中、失败、待人工均有文字标签；不只用红黄绿 |
| 如何支持讲解 | 结果先行、关键转折可见、对象可回溯 | 首屏展示“需求 → 计划 → 执行 → 产物”，每一步都可指着讲 |

## 4. 状态色观察与约束

GOV.UK Design System 将颜色按功能语义使用，并要求文本与交互元素满足 WCAG 2.2 AA；焦点色专用于焦点，不与警示混用。[颜色规范](https://design-system.service.gov.uk/styles/colour/) 本项目据此采用：

- 成功：绿色 + “已完成/已生效”文字；
- 警示/待确认：琥珀色 + “等待你确认”文字；
- 失败：红色 + 失败步骤与恢复动作；
- 处理中：蓝/青色 + 进度与当前步骤；
- 灰度中：中性灰/靛蓝 + 明确“灰度中”标签，不使用半透明来暗示；
- 键盘焦点：高对比描边，与任何业务状态色分离。

## 5. 对样张的直接输入

对话窗口样张应固定呈现以下层级：

1. 顶部：环境与“模拟数据”标识、当前 Agent 版本、运行状态；
2. 左侧：两大业务域导航 + 最近会话；
3. 中部：用户需求、已确认执行计划、2/4 进度、可打断动作、证据摘要；
4. 右侧：本次会话产生的正式对象及状态；
5. 底部：输入区与“工作台不会直接写入在线侧”的边界提示。

这套结构沿用阶段 3 的逻辑底稿，但视觉上重新建立密度、层级与状态语言。
