## 一、调研对象与分组

共 9 个对象:6 个产品 + 3 套有公开色值的官方设计系统,按我们产品形态的三类页面分组:

| 组 | 对象 | 对应我们的哪类页面 |
|---|---|---|
| AI 工作台 / Agent 平台 | Dify、Coze(扣子)、阿里云百炼、Salesforce Agentforce、LangSmith | 对话窗口、实验管理、Agent 配置、工具台、证据链、验证报告 |

## 二、AI 工作台 / Agent 平台组

### 2.1 Dify

- **导航**:左侧栏主导。入口:工作室、知识库、工具、探索;模型供应商 / 工具 / 数据源 / 触发器 / Agent 策略为次级入口。二级结构「应用列表 → 应用详情」。来源:https://enterprise-docs.dify.ai/zh/3.12.x/use/build/goto-anything
- **信息密度**:编排画布三栏——左节点库、中画布、右节点配置面板(官方文档未描述画布,此布局描述来自第三方教程,**推断**)。节点宽度固定 240px(第三方源码分析)。
- **对话与传统控件共存**:**分区共存,不叠层**。编排页右侧是独立「调试与预览」面板,内含聊天窗口 + Start 节点变量表单,对话与配置同屏并排、互不遮挡。
- **过程态呈现(最有价值)**:Run History 分三 Tab:**RESULT / DETAIL / TRACING**。TRACING 展示节点执行顺序、逐节点耗时、节点间数据流转、Token 消耗、失败节点定位;运行中通过 SSE 推送 `node_started` / `node_finished`;节点状态机 9 态。来源:https://docs.dify.ai/en/self-host/use-dify/debug/history-and-logs
- **配色**:官方无公开色彩规范。工作流状态色(灰 Waiting / 蓝 Running / 绿 Succeeded / 红 Failed / 橙 Stopped)来自第三方源码分析,**推断**。
- **可借鉴**:
  1. RESULT / DETAIL / TRACING 三 Tab = 「业务结论 / 执行明细 / 执行证据」物理分离 → 对应我们的**验证报告**(结论)与**证据链**(证据)两个视图;
  2. 画布右侧常驻预览,不跳页即可测;
  3. 全局搜索 ⌘K + 前缀过滤(`@app` / `@kb` / `@node`),模块多时比多级菜单快(可选,原型不硬做)。

### 2.2 Coze(扣子)

- **导航**:顶栏负责产品域(工作台、插件市场、知识库、工作流、卡片),空间内左栏负责「项目管理 / 集成管理 / 资源库」。来源:https://docs.coze.cn/cozespace_agent_management.md
- **布局**:Agent 编排页是中文 Agent 平台最典型的三栏——左「人设与回复逻辑」、中「技能/编排」、右「预览与调试」,口诀「左人设、中技能、右预览」(多份教程一致口径,**非官方文档**)。
- **对话共存**:对话即产品本体。Agent 设置不设独立页,挂在「对话窗口右侧导航 → `···` → Agent 设置」,配置抽屉**叠加在会话之上**,不打断上下文。会话内连接状态用**文字徽标**(在线 / 掉线了),不用纯色点。
- **配色**:Coze 底层是字节 Arco Design。官方设计变量(**官方文档值**):成功 #00B42A、警示 #FF7D00、错误 #F53F3F,每色 7 级梯度。来源:https://www.arco.design/react/docs/token
- **可借鉴**:
  1. 三栏骨架是中文用户已被教育过的布局,Agent 配置页可直接沿用,零学习成本;
  2. 配置抽屉叠加在会话上;
  3. **连接状态用文字而非纯色点**——风控场景里「Agent 离线」本身是风险信号,表达力要求更高。

### 2.3 阿里云百炼

- **导航(对本项目最重要的参照)**:双层。**顶栏切产品域**(模型 / 应用 / MCP / 文档 / API),**左栏切当前域内功能**。左下角固定「管理业务空间」。2026-09 官方公告称控制台「重构导航与核心流程,聚合能力入口,缩短操作路径」。来源:https://developer.aliyun.com/article/1662174
- **布局**:工作流编排页 = 左节点列表 + 画布 + 右下测试窗;Agent 配置页 = 模型选择器 + 系统提示词(支持变量)+ 右侧调试对话框。来源:https://help.aliyun.com/zh/model-studio/new-single-agent-application
- **对话共存**:右侧置调试对话框,不侵占配置区。与 Dify、Coze 三家**完全同构**。
- **配色**:控制台未见公开色彩规范。阿里系后台通用 Ant Design Token v5(**官方文档值**):success #52c41a、warning #faad14、error #ff4d4f、info 跟随主色 #1677ff。来源:https://ant.design/theme-editor-cn
- **可借鉴**:
  1. **「顶栏切域 + 左栏切功能」两级结构,几乎是为我们「AI 工作台 / 在线风控」双形态量身定制**——这是本调研对我们最重要的单条结论;
  2. 跨域开关放左下角固定位,不占主菜单额度。

### 2.4 Salesforce Agentforce Builder

- **导航**:三层。左「Navigation Explorer」固定五组分区(Settings / Subagents / Variables / Connections / Data);中 Editor View 以 Tab 形式在 Canvas(自然语言)与 Script(代码)间切换;右「Agentforce Assistant」AI 面板。来源:https://trailhead.salesforce.com/content/learn/modules/quick-start-assemble-a-service-agent-with-agentforce-builder/build-with-agentforce-builder
- **对话共存(最独特)**:右侧 Assistant 用自然语言**改配置**(产出待确认的变更提案);另有一个 Conversation Preview 面板用自然语言**测 Agent**。**两者职责严格分离**,避免「我在改配置」与「我在测效果」混淆。
- **过程态**:Conversation Preview 有 Live Test / Simulate 两档;Interaction Details 展示本次会话用了哪些 subagent、action、instruction 与推理链——即「Agent 为什么这么做」的可解释视图。来源:https://agentforcelens.com/en/article/agentforce-builder-canvas-script-guide
- **配色**:SLDS 有公开色板,但状态色官方取值页本次未检索到,**公开资料不足**。
- **可借鉴**:
  1. 左 Explorer 五组固定分区是 Agent 配置的稳定骨架 → 直接映射我们的 **Agent 配置页信息架构**(提示词 / 可调用工具 / 权限 / 边界 / 版本);
  2. 双对话分离(改配置 vs 测效果)——我们只有一个对话窗口,但这条提醒我们:**执行中的计划与「改配置」场景要有明确视觉区分**(改配置是待确认卡片,不是即时生效);
  3. Canvas / Script 双视图,给业务与工程师各一个入口(原型可选做)。

### 2.5 LangSmith(实验与证据链的闭环范本)

- **导航**:左栏 + 页内二级 Tab(Tracing / Evaluators / Automations)。左侧栏分节细节来自第三方教程,**非官方**。
- **信息密度**:运行列表固定 6 列(Name / Input / Output / Error / Latency / Tokens);实验结果表支持 **compact / full / diff 三档密度**切换,默认热力图着色反馈分数(红=低,绿=高)。来源:https://docs.langchain.com/langsmith/chat
- **对话共存**:LangSmith Chat 常驻**右下角悬浮层**,快捷键唤起,可在 Trace 页、Dataset 实验、标注队列、Evaluator 构建器中调用,读取 run 元数据来回答「这次为什么失败」——「AI 助手作为全局层」而非独立页面的典范。
- **闭环能力(最值得抄)**:Trace 上可直接「Add to Dataset」把线上失败样本一键转为评估集;「Run in Studio」跳转复现。来源:https://docs.langchain.com/langsmith/observability-studio
- **配色**:**公开资料不足**。
- **可借鉴**:
  1. **「线上 Trace → 一键入数据集」把事故沉淀为回归用例** = 我们「证据链 → 验证报告」要的闭环;
  2. 表格 compact / full / diff 三档密度,对高密度运营台非常实用;
  3. AI 助手做全局悬浮层 + 快捷键(我们的对话窗口是主界面,不走悬浮层,但「全局可唤起」的思路可参考)。

## 三、风控 / 反欺诈运营台组

### 3.1 Stripe Radar(部分推断)

- **导航**:Dashboard 左栏 → Radar 分组,含 Rules / Reviews / Insights / Performance 四子页;Rules 页内部再分四段(3D Secure / Allow / Block / Review),每段一个「+ Add rule」。来源:https://docs.stripe.com/radar/rules
- **布局**:复核队列是「列表 + 详情」两态。列表列:风险等级、客户、支付信息、金额、时间、client。详情三块:可自定义的支付上下文(metadata)、**risk insights(AI 判定最相关的风险因素)**、related payments(同邮箱 / 同 IP / 同卡的关联交易)。来源:https://docs.stripe.com/radar/reviews
- **证据链(本调研最有价值的单点)**:**「AI 给分 → 展示驱动分数的最相关风险因子 → 展开关联交易网络 → 人工裁决」**。配套:J/K 键切案件、`Assign to me` 认领防重复劳动、review timeline 记录操作历史;规则页有「Test Rule」先跑历史数据看影响面。来源:https://academy.usetoggle.com/en/articles/6085284-how-to-set-up-stripe-radar
- **配色**:官方未公布设计系统色值。品牌色 #635BFF 见于第三方汇总,**非官方文档值**;风险等级(normal / elevated / highest)的色值**公开资料不足,需目测推断**。
- **可借鉴**:
  1. **「判定 + 依据 + 关联网络」三段式证据区** = 我们案件详情页的主体结构;
  2. J/K 键盘流 + 认领机制(原型可不做键盘流,认领机制可提现为「去处置」按钮防重复);
  3. 规则先试跑历史数据再上线 = 我们的**策略灰度**。

### 3.2 AWS Fraud Detector(传统后台范式 + 可解释性)

- **导航**:控制台左栏固定九条(Data model explorer、Events、Labels、Entities、Variables、Models、Detectors、Outcomes、Search past predictions)——传统后台范式,**无对话能力**。来源:https://docs.aws.amazon.com/zh_cn/frauddetector/latest/ug/prediction-explanation.html
- **版本状态**:Detector 版本 **Draft → Active**,动作 Actions → Publish;规则执行顺序显式暴露 FIRST_MATCHED / ALL_MATCHED。
- **可解释性(最值得抄)**:Prediction explanations 用「**相对影响 0–5 星 + 方向**」表达——红色星号提高欺诈分、绿色星号降低、全 0 星无显著影响(底层 SHAP);可切「Show raw values」看原始 log odds。
- **配色**:官方未给出具体色值,**公开资料不足**。
- **可借鉴**:
  1. **星级 + 红绿方向的风险因子表达,比纯红绿块信息量大且色盲友好** → 可用于案件详情的「证据强度」;
  2. 「解释分 / 原始分」双档切换,让专家能下钻;
  3. Draft / Active 发布态语义 = 我们的「待注册 → 已生效」。

### 3.3 腾讯天御 RCP(灰度发布口径的唯一官方支撑)

官方产品页明确:决策引擎支持「策略 / 模型 / 变量在线更新,无需下线后再发布;支持**试运行 / 灰度 / 正式运行**完整生命周期;策略配置通过拖拽完成」。控制台具体界面与色值无公开文档,**公开资料不足**。来源:https://cloud.tencent.cn/product/rcp

**可借鉴**:这是「策略引擎配置 + 灰度发布」可直接引用的官方口径支撑;灰度的**色值**仍无公开参照,需自研(见设计基线)。

## 四、监控 / 运维台组(配色底座)

### 4.1 Grafana(暗色监控台配色底座,官方包文档值)

`@grafana/design-tokens` 公开 npm 包:primitive 以 OKLCH 编写,22 色相 × 11 级;semantic 层定义 **info / success / warning / danger** 四类状态意图,通过 `[data-color-mode]` 在明暗模式间运行时切换。来源:https://socket.dev/npm/package/@grafana/design-tokens/overview/0.2.0

暗色模式(**官方包文档值**,属 legacy 层,官方标注迁移期用):
- `background.canvas` = **#111217**(带蓝深灰,非纯黑)
- `text.primary` = **#CCCCDC**(非纯白)
- `border.medium` = **rgba(204, 204, 220, 0.16)**(半透明浅色,叠加不显脏)
- `primary.main` = **#3D71D9**

**可借鉴**:
1. 暗色监控台不要纯黑底——#111217 类带蓝深灰 + #CCCCDC 类非纯白文字,长时盯屏舒适度显著更好;
2. 边框用 16% 透明度的浅色而非实色;
3. **「状态意图四分类 + 明暗双模式」token 结构 = 我们两版样张的共同底座**。

### 4.2 Datadog LLM Observability(先定数据模型再定 UI 的范例)

- **布局**:Traces 视图 = 查询栏 + 结果列表,查询语法直接暴露属性(`ml_app:shopist-chat-v2 'purchase' @trace.total_tokens:>=20`);trace 详情是**火焰图**,点 span 出侧栏详情;开箱仪表盘分 Overview 与 LLM Calls 两段。来源:https://docs.datadoghq.com/llm_observability/investigate/
- **数据模型**:span 类型枚举 LLM / Workflow / Agent / Tool / Task / Embedding / Retrieval;trace 分三级复杂度(单次推理 / 固定工作流 / Agent 自主工作流)。来源:https://raw.githubusercontent.com/DataDog/documentation/7aa9fd22a9b149dd1d4b47c7d5e7652f9eee0443/content/en/tracing/llm_observability/core_concepts.md
- **配色**:官方未列状态色值,**公开资料不足**。
- **可借鉴**:
  1. span 类型枚举 + trace 嵌套层级 = 我们**任务队列 / 证据链**的数据骨架;
  2. 火焰图 + 侧栏 span 详情是展示 Agent 执行链的成熟范式(原型可用横向时间线简化表达);
  3. 语法化查询(`属性:值`、`-` 取反)适合专家,原型用筛选器即可。

## 五、状态色规范:官方可查值汇总

| 系统 | success | warning | error | info / 处理中 | 来源性质 |
|---|---|---|---|---|---|
| Arco Design | #00B42A | #FF7D00 | #F53F3F | — | 官方文档值 |
| Ant Design v5 | #52c41a | #faad14 | #ff4d4f | #1677ff(跟随主色) | 官方文档值 |
| Grafana(dark) | — | — | — | primary #3D71D9 | 官方包文档值 |
| Dify 工作流五态 | Succeeded 绿 | Stopped 橙 | Failed 红 | Running 蓝 / Waiting 灰 | 第三方源码分析,推断 |
| **灰度 / 发布中** | **所有调研对象均未公开色值** | | | | 公开资料不足,需自研 |

跨产品共性规律:**语义四分类(success / warning / error / info)是事实标准,「处理中」统一用蓝(或跟随主色);具体色值各家不同。** 且出现一个值得注意的反例:AWS 用「星级 + 红绿方向」表达风险因子影响力而非纯色块,色盲友好度更高——我们案件详情的「证据强度」将借鉴。

## 六、跨产品共性模式(四维总结)

1. **导航:左侧栏是绝对主流,顶栏只负责「切产品域」。** 单侧栏 + 页内二级 Tab:Dify、Coze、Stripe、AWS、LangSmith。双层(顶栏切域 + 左栏切功能):阿里云百炼。三栏工作区(左导航-中编辑-右预览):Coze、Dify、百炼、Agentforce。一级条目普遍 **5–9 个**(Agentforce 五组、AWS 九条、Dify 五条),超出即用分组或二级 Tab 折叠。
2. **信息密度:一屏 3–5 个信息块,主视图一律「表格 / 列表 + 详情抽屉 / 侧栏」两态。** 没有一家用卡片瀑布做主视图(Stripe 复核队列、LangSmith run 列表、Datadog span 侧栏、AWS 资源列表)。密集内容默认折叠、按需展开。共性是**先把数据模型定死再做高密度 UI**。
3. **对话与传统控件:分区共存,绝不叠层。** 最一致的惯例是「配置在左/中,对话预览固定右侧」(Coze、Dify、百炼、Agentforce 四家完全同构)。且对话的两个职责被拆开:改配置的助手与测效果的预览是**两套东西**;全局 AI 助手做成常驻悬浮层 + 快捷键而非独立页面。(我们的对话窗口是主界面、不叠层更不悬浮——但「配置在左、对话在右」的对照关系可映射为「对话流在左、对象栏在右」。)
4. **状态色:语义四分类 + 处理中=蓝是事实标准;灰度色无公开参照需自研;红/绿方向编码对色盲更友好。**

## 七、对阶段 4 的借鉴映射(结论)

| 调研发现 | 落到我们哪里 |
|---|---|
| 百炼「顶栏切域 + 左栏切功能」 | **整体信息架构**:顶栏切「AI 工作台 / 在线风控」,左栏切当前域内功能——且这个域切换本身就是演示叙事点(工作台产包 → 切到在线侧 → 人确认生效) |
| Dify「RESULT / DETAIL / TRACING」三 Tab | 验证报告(结论)/ 证据链(证据)两视图的分工依据 |
| LangSmith「Trace → 一键入数据集」闭环 | 证据链 → 数据集管理 → 验证报告的闭环叙事 |
| Stripe「判定 + 依据 + 关联网络」三段式详情 | 案件详情页主体结构 |
| AWS「星级 + 红绿方向」+ Draft/Active | 案件详情「证据强度」表达;待注册 → 已生效状态语义 |
| Datadog「span 枚举 + trace 嵌套」 | 证据链 / 任务队列的数据骨架 |
| Grafana 暗色 token(#111217 / #CCCCDC / 16% 边框) | 深色监控台版样张的配色底座 |
| Arco / Ant 官方状态色 | 浅色业务后台版样张的状态色校准参考 |
| Agentforce 双对话分离 | 对话窗口里「改配置」必须走待确认卡片、绝不即时生效 |
| 腾讯天御「试运行 / 灰度 / 正式运行」 | 策略引擎配置页灰度态的口径支撑(色值自研) |

**两个影响方案的关键结论**:
1. 「AI 工作台 + 风控运营台」双产品形态,百炼的顶栏切域 + 左栏切功能是唯一现成的、可直接照搬的两级结构参照;
2. 「证据链 → 验证报告」主线,Stripe(判定+依据+关联网络)与 LangSmith(Trace→入数据集→回归实验)各解决一半,拼起来即完整闭环。
