# 阶段 4 产品参照调研

> 项目边界：本项目是个人作品集 Demo，使用抽象业务场景与虚构模拟数据；本文只讨论可借鉴的界面组织，不代表作者曾在任何真实公司主导、上线或运营同类产品。
>
> 调研日期：2026-09-17｜证据类型：产品官方文档与官方界面说明｜厂商能力描述均视为厂商自述，不作独立效果背书。

## 1. 调研问题与结论

本轮不是寻找一套可直接照搬的“万能后台”，而是回答五个具体问题：导航怎样切、密度怎样分层、对话怎样与传统控件共存、运行状态怎样持续可见、风控处置怎样保持可追溯。

结论是采用一套“三层操作台”：

1. **稳定壳层**：左侧一级导航固定分为「AI 工作台 / 在线风控」，不让对话承担全站导航。
2. **任务工作层**：中间对话流承载需求、计划、确认、进度、失败和结果；消息不是气泡堆叠，而是结构化操作卡。
3. **对象与证据层**：右栏固定显示本次会话生成的实验、任务、证据链、报告和待审批包，点击进入传统页面深看。

这套结构同时借鉴 AI 工作台的“会话 + 过程可视化”和风控后台的“队列 + 详情 + 可审计动作”，但不复制任何产品的品牌视觉。

## 2. 参照产品

### 2.1 Microsoft Copilot Studio：对话与结构化画布并行

**官方可核实形态**

- 官方测试说明把 Test agent 作为侧面板；用户可在面板中继续对话，同时保留主编辑上下文。
- 点击某条 agent 回复，会定位到产生回复的 topic 与 node；被触发的节点会出现明确标记。
- generative orchestration 可在 activity map 中展示实时计划；变量也能在测试期间展开观察。
- 官方明确提示测试面板并不等同于已发布渠道的完整行为。

**可借鉴**

- 对话与结构化对象不应二选一：对话负责发起与串联，节点/对象负责定位与深查。
- 用户点一条结果后，应能跳到对应实验、任务或证据链，而不是停留在一段文字里。
- 把“执行计划、工具步骤、状态”可视化，但只展示可审计活动，不展示隐藏推理过程。
- Demo 必须保留“演示环境 / 模拟数据”标签，不能把原型测试态包装成线上系统。

**不照搬**

- 本项目不是 Agent 编排器，不把 node graph 作为主界面；主界面仍是风控运营任务。
- 不使用大面积低密度聊天气泡，也不暴露 chain-of-thought。

来源：[Test your agent](https://learn.microsoft.com/en-us/microsoft-copilot-studio/authoring-test-bot)

### 2.2 LangSmith：Trace 是调试与评估的共同锚点

**官方可核实形态**

- 官方将 trace 定义为 agent 执行记录，并提供 UI/API 中的筛选、导出、共享和对比。
- observability 同时包含 dashboard、alert、rule、webhook、online evaluation 与 annotation queue。
- 单次 trace 与全局质量指标处在同一个观测体系中。

**可借鉴**

- 每次对话执行必须生成正式对象；会话只是入口，对象才是后续查找、对比、验收的载体。
- 嵌入式证据链用“步骤 + 工具 + 时间 + 结果状态”表达；深查时进入独立证据链页面。
- 把失败步骤、跳过步骤和已完成步骤同时保留，便于从失败点续跑，而不是清空上下文。
- 全局监控负责发现异常，单条 trace/证据链负责解释“这一笔发生了什么”。

**不照搬**

- 本项目数据为模拟，不使用“production trace”“线上效果”等可能造成误解的文案。
- 不把可观测性产品的开发者术语直接暴露给风控运营用户。

来源：[LangSmith Observability](https://docs.langchain.com/langsmith/observability)

### 2.3 Stripe Radar：风险队列采用“列表扫描 → 单笔深查 → 明确动作”

**官方可核实形态**

- Review queue 是按优先级组织的可疑支付列表，并提供 list view 与 detailed view。
- 详情可展示风险上下文与关联支付；用户可以 Previous / Next 连续处理队列。
- review assignment 用于避免重复劳动，timeline 记录分配变化与其他动作。
- 队列动作有清晰结果，例如 approve、refund、report fraud；规则可把特定对象自动送入 review。

**可借鉴**

- 实时监控下钻后使用主从结构：左侧/上方高密列表用于扫描，详情区用于证据和处置。
- 状态、负责人、进入队列原因与积压时间必须在列表层就可见，不强迫逐条打开。
- 每个处置动作都要有后果说明和历史记录；危险动作必须与普通浏览动作视觉分级。
- “相关对象”作为详情的一部分，帮助用户判断是否为孤立事件或关联手法。

**不照搬**

- 不复刻支付退款、卡指纹等 Stripe 专属对象；本项目保持抽象的转账案件与风险主体。
- 不用真实商户、真实卡号或真实处置结果。

来源：[Transaction reviews](https://docs.stripe.com/radar/transaction-reviews)、[Radar rules](https://docs.stripe.com/radar/rules)

### 2.4 Datadog Dashboards：高密监控依靠网格与全局筛选保持秩序

**官方可核实形态**

- 官方将 dashboard 定义为集中查看实时指标、趋势、异常和根因线索的界面。
- 支持 widget、query、overlay 和 template variable；template variable 可动态过滤整张看板。
- grid layout 适合状态板与叙事视图，最多 12 个网格列；automatic/free-form layout 用于排障和探索。
- widget 类型覆盖 timeseries、query value、top list、table、distribution 等。

**可借鉴**

- 实时监控采用 12 列网格：首屏先放 4–7 个紧凑指标，再放趋势、分布和异常队列。
- 时间窗、案件类型、版本等放在全局筛选条，不在每张卡重复。
- 把“状态板模式”和“下钻排障模式”分开：前者稳定，后者允许更自由的筛选与对比。
- 状态颜色只用于异常与进度，不让所有卡片都高饱和。

**不照搬**

- 不追求运维大屏式炫技，不使用满屏折线和发光效果；作品主轴仍是可讲的产品流程。
- 不宣称页面数字实时刷新；Demo 中统一标为模拟快照或模拟执行。

来源：[Datadog Dashboards](https://docs.datadoghq.com/dashboards/)

## 3. 横向归纳

| 维度 | 成熟产品共同做法 | 本项目采用 |
|---|---|---|
| 导航 | 稳定一级导航；任务上下文在页面内展开 | 左栏分「AI 工作台 / 在线风控」，顶栏只放上下文与全局状态 |
| 信息密度 | 列表负责扫描，详情负责解释，侧栏负责上下文 | 对话主区 + 本次会话对象栏；监控页采用指标 → 趋势 → 案件队列 |
| 对话与控件 | 对话发起，结构化面板确认与深查 | 计划卡、待确认卡、进度条、证据链折叠块、对象链接 |
| 状态可见 | 状态贴近对象，持续显示，不依赖 toast | 执行中/审批中/灰度中/失败等用“颜色 + 图标 + 文字”，toast 只作补充 |
| 可追溯 | trace/timeline/activity 串起过程与结果 | 每次执行生成对象 ID；失败与旧参数结果均保留并标注 |
| 高风险动作 | 语义明确、后果可见、历史可查 | 对话不直接生效；注册和授权只生成待审批包，在线侧由人确认 |

## 4. 对风格样张的直接输入

- 样张使用同一信息架构输出深浅两套皮肤，避免把“主题选择”与“布局选择”混在一起。
- 首屏必须同时看见：用户需求、四步执行计划、执行进度、插话/暂停反馈、本次生成对象、模拟数据标识。
- 深色版强调运行态与过程观测，适合讲“系统正在做什么”；浅色版强调表单、对象与审批，适合讲“业务人员如何操作”。
- 两版都不做霓虹科幻风，不用渐变大标题，不用巨型空白；视觉重点是信息层级和状态可信度。
