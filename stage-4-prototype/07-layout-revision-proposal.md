# 界面信息层级重排提案

> 日期：2026-09-18  
> 性质：阶段 4 高保真原型改版规格；只定义实施边界，不代表 HTML、截图或设计基线已经修改。  
> 依据：`prototype/samples/sample-dialog.html`、四张 1200×960 截图、`stage-4-prototype/03-design-baseline.md`、`stage-3-features/03-dialog-spec.md`、`stage-3-features/01-feature-list.md`。

## 0. 结论先行

三条产品反馈成立。实施规格收敛为六项决定：

1. 默认产品界面移除七态演示条；URL 只作为测试入口。
2. 状态拆为 `sessionPhase`、`runState`、`workspaceMode` 三个正交轴；补齐“待确认”和 URL 可直达的“暂停”。
3. **右栏是运行中实时步骤的唯一主视图**；主区计划在确认后折叠为一行历史摘要，不再重复进度条和四步详情。
4. 274px 右栏按 242px 净内容宽度设计：只显示最新产出的标题、列表和 4–6 行摘要；表格、代码与完整正文只在主区查看态出现。
5. 输入改为 `<textarea>`，打通“提交 → 受理 → 待确认 → 确认 → 执行”的真实会话节拍。
6. 删除泛化免责声明，但保留当前能力事实和决策点状态；第三栏按页面任务条件出现，不再作为 14 个界面的强制骨架。

```text
新会话                       活跃会话
┌────────主区────────┐       ┌────────主区────────┬────执行侧栏────┐
│ 任务导向文案        │       │ 用户消息            │ 状态与更新时间 │

│ 示例指令            │       │ 待确认计划 / 历史摘要│ 最新产出短预览 │

                             └─────────────────────┴────────────────┘
```

## 1. 负责人原话

> 1. 正常,加载,超时这一行不应该是这么醒目和占空间的提醒,不太符合一个合理的平台交互重要性的信息排布
> 2. 主对话框只看到了卡片,不知道正常输入文本的交互样式,符不符合目前主流的chatbot体验和审美
> 3. 我理解右侧的展开是为了给用户实时同步agent执行工作的进度,并进行了可视化,需要保留一些方案展示,比如md文件等,同时不需要提醒在线端无法在这里操作的信息,这是产品设计的规范无需解释

## 2. 问题一：演示状态不应成为产品导航

### 2.1 诊断

`.statebar` 是评审七态的测试控制器，却占用 52px 独立栅格行，并拥有完整的 active、hover 和异常红色态。它会被理解为用户可切换的业务模式，视觉权重高于实际输入和执行内容。问题不是七态覆盖，而是把测试入口混入产品信息架构。

### 2.2 方案

- 默认产品视图删除 `.statebar` 及其栅格行，主区由“标题 / 演示条 / 内容 / 输入”改为“标题 / 内容 / 输入”。
- URL 继续支持测试直达；如评审现场必须鼠标切换，只在 `?demo-controls=1` 显示单按钮“演示状态”菜单。菜单悬浮于产品布局之外，不进入正式截图。
- 错误、超时、阻止等高权重状态只在对应任务内容和执行侧栏出现，不在顶部重复着色。
- 非对话页面按各自业务状态设计，不复制同一排演示按钮。

### 2.3 对 11 个 A 档界面的影响

11 个 A 档界面统一遵守“测试控制不进入产品框架”。状态可以由 URL、fixture 或 QA 控制器进入，但必须显示在发生问题的对象附近。对话页的状态模型可复用设计方法，不能把对话专用枚举强加给监控、配置或列表页。

## 3. 状态模型：拆开会话阶段、任务状态与工作区模式

### 3.1 诊断

现有 `appState.view` 同时承担“是否已有会话”“任务正在做什么”“当前显示什么界面”，语义混编：

- `empty` 被同时理解为新会话和无结果；
- `normal` 实际等于运行中，但名字不表达任务状态；
- `paused` 只存在于 `appState.run`，URL 无法直达；
- 阶段 3 明确要求的“待确认”没有第一等状态，计划卡却直接写“已确认”；
- `outputViewer` 若继续塞入同一状态枚举，会让打开文档改变任务运行状态。

因此不采用“复用 `empty` 当新会话业务状态”的旧方案。`empty` 只保留为兼容测试入口，解析后映射到新会话，不进入内部语义。

### 3.2 三轴模型

```js
appState = {
  sessionPhase: 'new' | 'active',
  runState: 'idle' | 'accepting' | 'awaitingConfirm' | 'running' |
            'paused' | 'cancelled' | 'succeeded' | 'failed' | 'timedOut' | 'blocked',
  runFlags: { degraded: false },
  workspaceMode: 'conversation' | 'outputViewer',
  currentStep: 0,
  updatedAt: '23:08',
  draftText: '',
  messages: [],
  plan: null,
  executionSteps: [],
  latestOutput: null,
  objects: []
}
```

约束：

- `sessionPhase:new` 只能配 `runState:idle`。`active + idle` 表示“已有会话，但当前没有计划或任务”，只由任一终态后的纯问答进入；终态发生当下仍保留 `cancelled / succeeded / failed / timedOut / blocked`，直到用户发起下一条非执行型问答。列表“无结果”使用组件自己的 `contentState:noResults`，不得复用会话阶段。
- `workspaceMode` 只改变主区呈现，不改变 `runState`；查看文档时任务可以继续运行。
- 每次状态变化由一个 transition 更新模型，再由同一次 `render()` 同步主区、右栏、对象状态与时间戳；禁止局部改 DOM 文案。
- `awaitingConfirm` 是第一等状态；确认前不创建可执行任务，不显示“已确认”，也不自动进入 `running`。
- 降级不是任务生命周期节点：可选工具失败后保持 `runState:running`，只设置 `runFlags.degraded=true`；任务仍可继续并最终进入 `succeeded` 或失败终态。
- `new + outputViewer` 只允许由带 `mode=output&output=...` 的直接链接进入；关闭后回到 `new + idle + conversation`，普通新会话不能从空首屏打开不存在的产出。

### 3.3 URL 测试入口与阶段 3 七态对账

| URL | 内部映射 | 阶段 3 语义 | 说明 |
|---|---|---|---|
| `?state=empty` | `new + idle` | 空态 | 兼容测试别名；内部不保存为 `empty` |
| `?state=loading` | `active + accepting` | 受理中 | 显示用户消息与“正在核对数据集、工具与授权…” |
| `?state=confirm` | `active + awaitingConfirm` | 待确认 | 新增直达；计划可确认、改参数、取消 |
| `?state=normal` | `active + running` | 执行中 | 兼容现有主状态别名 |
| `?state=paused` | `active + paused` | 执行被打断 | 新增直达；旧结果标注来源 |
| `?state=completed` | `active + succeeded` | 执行完成 | 正式对象与验证报告已生成，可继续问答或查看产出 |
| `?state=error` | `active + failed` | 执行失败 | 失败步骤、保留结果与恢复动作 |
| `?state=unauthorized` | `active + blocked` | 需求无法受理 | 未授权工具禁用；0 次调用 |
| `?state=timeout` | `active + timedOut` | 执行失败的超时分支 | 必需工具超时并转人工 |
| `?state=degraded` | `active + running`，`degraded=true` | 执行中的降级分支 | 可选工具失败，显式缺失后继续 |

阶段 3 的七类界面语义仍由这些内部状态覆盖；`succeeded` 补齐任务生命周期终点，`timedOut` 和降级标记是已存在的可见业务分支。URL 参数是演示投影，不再被称为“七态唯一状态源”。

### 3.4 Transition 表

| 事件 | 前置状态 | Guard | 后继状态 | UI 结果 |
|---|---|---|---|---|
| 打开新会话 | 任意测试 fixture | `state=empty` | `new + idle + conversation` | 居中 textarea；不创建对象 |
| 首次提交 | `new + idle` | trim 后非空且不在 IME composition | `active + accepting` | 追加用户消息；composer 直接重排到底部；出现受理消息 |
| 受理中再次提交 | `active + accepting` | trim 后非空 | 状态不变 | 追加补充消息；不重启 1.2s 计时器、不生成第二份计划 |
| 受理完成 | `active + accepting` | 固定 1.2s 到时，或 demo 控制点击“下一步” | `active + awaitingConfirm` | 显示待确认计划；默认不自动执行 |
| 确认首次计划 | `active + awaitingConfirm` | 点击按钮，或 trim 后文本精确等于“确认”/“确认执行” | `active + running` | 计划折叠；创建 `#T-882` 等执行对象；右栏进入实时步骤 |
| 修改待确认计划 | `active + awaitingConfirm` | 点击“改参数” | 状态不变 | 原地展开参数表单；保存后回待确认计划 |
| 取消待确认计划 | `active + awaitingConfirm` | 点击“取消” | `active + cancelled` | 计划标记已取消；不创建执行任务；composer 可继续输入 |
| 终态/空闲后发起新执行需求 | `active + cancelled/succeeded/failed/timedOut/blocked/idle` | 意图被识别为执行型且非空 | `active + accepting` | 追加用户消息并生成新计划；沿用当前会话 ID；终态对象留作历史，不并入新任务 |
| 终态后普通追问 | `active + cancelled/succeeded/failed/timedOut/blocked` | 意图为只读问答 | `active + idle` | 追加普通问答；不创建计划或对象 |
| 运行中追加参数 | `active + running` | 意图为修改正在执行的参数 | `active + awaitingConfirm` | 立即挂起后续步骤；在途结果标“基于旧参数”；显示变更确认卡 |
| 确认运行中变更 | `active + awaitingConfirm` | `plan.previousRun` 存在且确认 guard 通过 | `active + running` | 从约定步骤重跑；旧参数结果保留但不并入新结论 |
| 取消运行中变更 | `active + awaitingConfirm` | `plan.previousRun` 存在且点击取消 | `active + running` | 恢复原参数执行；移除“等待变更确认” |
| 暂停 / 继续 | `running / paused` | 当前任务存在 | `paused / running` | 右栏步骤、对象、摘要按钮和时间戳同步 |
| 取消执行 | `active + running/paused` | 从“更多任务操作”选择“取消执行”并二次确认 | `active + cancelled` | 停止派发后续步骤；向在途步骤发取消请求；无法撤回的迟到结果只挂在已取消任务的证据记录中，不并入结论 |
| 可选工具失败 | `active + running` | 工具被标为 optional | `active + running`，`degraded=true` | 步骤标证据缺失，其余继续 |
| 降级原因消失 | `active + running`，`degraded=true` | 可选工具恢复且尚可安全重试 | `active + running`，`degraded=false` | 重试该步骤；不改任务阶段 |
| 必需执行步骤失败 / 超时 | `active + running` | 必需步骤返回失败或超过 fixture 时限 | `active + failed/timedOut` | 主区给恢复动作；右栏给失败或超时摘要 |
| 受理被阻止 | `active + accepting` | 预检发现工具未授权或需求越过只读范围 | `active + blocked` | 停止受理；保持 0 次未授权调用；给“生成授权包”入口 |
| 从失败或超时恢复 | `active + failed/timedOut` | 用户选择重试、换工具或人工确认继续 | `active + running` | 从明确恢复点继续；既有结果保留且标来源 |
| 阻止后生成授权包 | `active + blocked` | 点击“生成授权包” | 状态不变 | 新增待审批包对象；仍保持 0 次未授权调用，不自动重试 |
| 授权批准同步 | `active + blocked` | 对应审批包由在线侧批准且原请求仍有效 | `active + accepting` | 重新执行授权与范围预检；审批包保留为审计历史；阻止发生在执行前，因此没有旧执行结果可合并 |
| 全部步骤完成 | `active + running` | `completedSteps === totalSteps` | `active + succeeded` | 右栏显示完成；正式对象和 `#R-4517` 可查看 |
| 打开完整产出 | 除无产出的普通 `new` 外 | 产出 ID 存在，或为允许的直接链接 fixture | `workspaceMode:outputViewer`，runState 不变 | 主区替换为只读查看态 |
| 关闭完整产出 | `workspaceMode:outputViewer` | Escape / 返回 / history | `workspaceMode:conversation`，runState 不变 | 恢复草稿与滚动；焦点归还触发按钮 |

`accepting → awaitingConfirm` 的 1.2s 只用于高保真演示，不声称真实系统时延。自动计时与 demo 手动步进互斥；手动模式不启动计时器。

进入 `cancelled / succeeded / failed / timedOut / blocked` 任一终态时，reducer 必须原子清除 `runFlags.degraded=false`；已发生的可选工具缺失仍保留在对应步骤和证据历史中，但不继续把终态标成“降级执行”。

### 3.5 顶部任务动作按钮文案

| `runState` | 按钮文案 | 可用性 |
|---|---|---|
| `idle` | 尚未开始 | 禁用 |
| `accepting` | 正在受理 | 禁用 |
| `awaitingConfirm` | 等待确认 | 禁用；确认动作在计划卡内 |
| `running` | 暂停任务 | 可用；`degraded=true` 时仍可暂停 |
| `paused` | 继续任务 | 可用 |
| `cancelled` | 已取消 | 禁用 |
| `succeeded` | 已完成 | 禁用 |
| `failed` | 执行已停止 | 禁用 |
| `timedOut` | 等待人工 | 禁用 |
| `blocked` | 未获授权 | 禁用 |

`running` 与 `paused` 的顶部主按钮仍分别是“暂停任务”与“继续任务”；同一区域的“更多任务操作”菜单提供次级入口“取消执行”。该入口不与主动作并列抢占视觉权重，选择后必须二次确认。

## 4. 问题二：输入必须产生真实会话闭环

### 4.1 诊断

当前输入提交只弹 toast 并清空；没有追加用户消息、助手承接、待确认计划或状态迁移。计划卡又直接写“已确认”，跳过了首次受理必须确认的节拍。源码也没有让新会话输入框获得焦点。负责人看到的不是单纯“输入框不醒目”，而是输入没有成为交互主线。

### 4.2 输入组件

- 把单行 `<input>` 改为 `<textarea>`；初始 64px，可自动增高至 144px。
- `Enter` 发送，`Shift+Enter` 换行；中文输入法处于 composition 时 Enter 不发送。
- 空白输入不提交，保留焦点并给就地提示；发送按钮继续保持 44×44px。
- `sessionPhase:new` 时，composer 位于内容区顶部约 38%–45%，宽度 `min(720px, calc(100% - 48px))`；下方只有 3 条填充输入框的示例指令。
- 首次提交后复用同一个 composer，移动到主区底部固定位置；不创建第二套输入节点。
- 位置迁移采用同一 DOM 节点的网格区域切换与直接重排，不做跨屏位移动画；可选的内容淡入不超过 150ms，`prefers-reduced-motion` 下取消。这样不引入双输入框、焦点复制或布局追踪问题。

### 4.3 首次提交完整节拍

| 步骤 | 状态迁移 | 用户看到什么 | 焦点与播报 |
|---:|---|---|---|
| 0 | `new + idle` | 居中 textarea、任务导向文案、3 条示例 | 页面加载后 `textarea.focus()`；若 URL 带 viewer 或恢复态则不抢焦点 |
| 1 | 点击发送或 Enter | 立即把输入快照追加为用户消息；不先清空再丢失内容 | 提交成功后清空 textarea；焦点暂留 textarea |
| 2 | `active + accepting` | composer 固定到底部；助手文本“正在核对数据集、工具与授权…” | `aria-live="polite"` 播报受理；不靠 toast 代替消息 |
| 3 | `active + awaitingConfirm` | 助手给 1–2 句承接；展开待确认计划，显示步骤、范围、预计耗时、`确认执行 / 改参数 / 取消` | 计划标题容器设 `tabindex="-1"`；若 textarea 仍获焦且已有新草稿或处于 composition，只用 `aria-live` 播报，不抢焦点，否则聚焦计划标题；随后可 Tab 到三个动作 |
| 4A | 点击“确认执行”或在 textarea 回复“确认” | 计划原地变为“计划 v2 · 已确认 · 4 步”的一行摘要 | `runState → running`；焦点落到折叠计划摘要按钮，右栏礼貌播报开始执行 |
| 4B | 点击“改参数” | 计划卡原地展开参数表单，不进入执行 | 焦点到首个参数字段；保存后仍回 `awaitingConfirm` |
| 4C | 点击“取消” | 计划标记“已取消”，会话保留 | `runState → cancelled`；焦点回 textarea，可重新描述需求 |
| 5 | `active + running` | 主区继续对话和结构化结果；右栏独占实时步骤 | composer 保持可输入，可用于暂停、追加参数或追问 |

`accepting` 的唯一助手文案为“正在核对数据集、工具与授权…”。URL fixture、自然提交和实施时的 `prototype/samples/sample-dialog.html` 均以此规格为准，不再保留“正在理解需求”的变体。

直接 URL 进入 `confirm` 时也必须渲染完整上下文：用户请求、助手承接、待确认计划；不能只出现孤立卡片。文本确认只接受 trim 后**精确等于**“确认”或“确认执行”的输入，且仅在 `awaitingConfirm` 生效；其他包含“确认”的句子按普通补充处理。执行中的再次提交按意图生成普通追问、追加参数或待确认变更，不绕过机制二。

### 4.4 主流 chatbot 体验与操作台边界

保留用户消息和简短助手文本，使“输入—回应”可被识别；确认、参数、进度、证据和恢复仍由结构化组件承担。不改成纯气泡聊天，也不把长解释塞进助手消息。

## 5. 问题三：执行侧栏与产出展示

### 5.1 唯一进度主视图

采用以下固定分工：

- **待确认前：主区是计划主视图。** `awaitingConfirm` 时完整计划卡只在主区出现；右栏仅显示“等待确认”，不复制四步计划。
- **确认后：右栏是实时步骤唯一主视图。** `running`（含 `degraded=true`）、`paused / failed / timedOut` 的四步时间线、当前步骤、更新时间只在右栏展示。
- **主区只留历史摘要。** 计划确认后折叠成一行“计划 v2 · 已确认 · 4 步 · 查看”；删除主区持续进度卡和重复的四步展开。点击“查看”可展开历史计划，但不显示实时高亮和第二条进度条。
- **异常动作仍在主区。** 失败原因、改参数、重试、换工具属于需要用户处理的会话事件；取消执行则从顶部“更多任务操作”进入。右栏只显示对应步骤的失败摘要和状态，不复制操作入口。

理由：右栏持续可见，适合实时扫描；主区是时间顺序的会话记录，适合保存“何时确认了什么”和承载用户决策。这样消除“计划卡 + 进度卡 + 右栏时间线”的进度三连。

确认后的主区不是空壳，按下表保留会话与结构化结果：

| 主区内容 | 出现条件 | 作用 | 与实时进度的边界 |
|---|---|---|---|
| 用户消息 | `active` 全程 | 保存需求、追问与确认原文 | 不显示步骤状态 |
| 助手承接 | 每次受理或决策后 | 解释下一动作与所需输入 | 不复述 `2 / 4` 或当前步骤 |
| 折叠计划摘要 | 首次确认后 | 保存“确认了哪份计划”的历史 | 可展开计划定义，但无实时高亮、进度条和更新时间 |
| 工具选择 / 授权机制卡 | 存在候选工具或授权决策时 | 保存候选、选择理由和确认结果 | 是决策快照，不是执行步骤列表 |
| 证据链机制卡 | 首条可审计证据生成后 | 保存工具、输入摘要、结果、时间和归属对象 | 是不可变的调用证据记录；不显示“当前步骤”或实时高亮 |
| 中断反馈卡 | 暂停、参数变更或恢复时 | 记录中断原因、旧参数结果和恢复点 | 是会话事件，不持续刷新进度 |
| 失败 / 恢复卡 | `failed / timedOut / blocked` | 说明失败事实并承载恢复动作 | 右栏只给失败摘要，不复制动作 |

“证据链卡”与右栏时间线是不同对象：前者回答“哪次工具调用留下了什么可审计证据”，后者回答“编排目前走到哪一步”。证据卡一经生成只追加或引用，不跟随当前步骤改色；右栏步骤可以实时变化，但不承载完整输入、结果和证据正文。

运行态示例：`调用 #C-17 · 企业名单查询 · 23:08 · 输入 120 行 · 命中 7 条 · 归属 #E-2041`。该证据卡不出现步骤序号、`2 / 4`、处理中高亮或预计剩余时间，避免被实现成右栏步骤的加宽版。

### 5.2 242px 净宽下的内容上限

当前右栏外宽 274px，左右各 16px 内边距后净内容宽约 242px。该宽度不能可靠承载 Markdown 表格或代码块，因此规格限定为：

- 顶部：当前状态、`2 / 4`、更新时间；
- 实时步骤：每行只含序号、短标题、状态；时间只给完成项和当前项；
- 最新产出：只显示文件名、归属对象、更新时间、一个标题和 4–6 行段落/列表摘要；固定最大高度约 180px；
- 相关对象：类型、ID、当前状态的紧凑行；不再保留 featured 主对象卡；
- 不在列内显示表格、代码块、长引用、目录、多产出切换器或横向滚动。

右栏只预览**最新产出一项**。其他产出通过紧凑对象行进入对应界面，不在 242px 内做 tab、carousel 或文件切换器。

### 5.3 Markdown 命名与冻结对象模型对账

`验证方案.md` 不定义为新的正式对象类型。它是任务组 `#T-882` 的只读“计划快照”，展示名写为：

`任务附件 · 验证方案.md · 归属 #T-882 · 模拟草稿`

其内容来自已确认执行计划，用来演示 Agent 产出可阅读；没有独立对象 ID、生命周期或新页面。正式结论仍落到冻结对象 `验证报告 #R-4517`，完成后右栏最新产出可切换为该报告摘要。实施不得把 `.md` 文件与验证报告并列成第五类正式对象。

### 5.4 当前能力事实与泛化免责声明的边界

**删除：** `在线侧边界` 长段落、重复的“对话不能直接修改在线配置”、把产品规范写成免责声明的说明块。

**保留：** 用户当前决策需要的能力事实和对象状态：

- 有右栏时在底部一行显示：`运营助手 Agent · v3.2 · 在线侧只读 · 3 工具可用`；新会话和受理中尚未启用右栏时，同一句压缩信息放在 composer 下方；
- 未授权候选行：`工商股权穿透查询 · 未授权 · 不可调用`；
- 审批对象行：`待审批包 #P-xxx · 未生效`；
- 越权态：`未授权调用 0 次`，并给“生成授权包”入口；
- 全局继续保留“个人作品 · 虚构模拟数据”。

能力事实使用普通辅助文字，不使用 warning 容器；真正待确认、超时和待审批才使用琥珀。这样删掉解释性代偿，同时不静默丢失只读范围、工具可用数和未生效状态。

### 5.5 右栏状态 / 隐藏矩阵

| 测试入口 | 侧栏顶部 | 步骤区 | 最新产出 | 对象 / 能力事实 |

`unauthorized` 中生成授权包后，右栏对象行改为“待审批包 #P-xxx · 未生效”，状态仍为 `blocked`。在线侧批准事件同步后按 §3.4 回到 `accepting` 重新预检，不直接跳到 `running`，也不复用被阻止前不存在的执行结果。

## 6. 完整产出查看态

选择**替换主区的页面内查看态**，不是模态框，也不在右栏内嵌套第二层抽屉。

- 点击“打开完整方案”后，`workspaceMode → outputViewer`；左导航与右侧执行栏保持，主区替换为只读文档。
- 查看态顶部包含返回按钮、`验证方案.md`、归属 `#T-882`、更新时间和“模拟草稿”；正文可滚动，允许标题、列表、表格和代码片段。
- 打开时用 `history.pushState()` 写入 `?mode=output&output=plan-snapshot`；浏览器后退和主区“返回对话”均恢复 `conversation`。统一的 query 读写器同时保留并回读 `theme / state / mode / output / demo-controls`，取代当前只序列化 `theme / state` 的 `syncQuery`。
- `theme`、状态 fixture 和 demo 步进使用 `replaceState()`，打开产出使用 `pushState()`；`popstate` 一次解析全部参数、更新三轴与 flag 后只调用 `render()`，不得在处理器内再次写 history。非法组合按 §3.2 约束归一化，并在 reload、后退、前进和直接链接中得到同一结果。
- 若从站内会话打开，关闭调用历史返回；若直接 URL 打开，关闭使用 replace 回默认会话，不能把用户送出样张。
- Escape 返回会话；焦点进入查看态主标题。返回后焦点归还右栏“打开完整方案”按钮。
- 因为不是模态框，不做焦点圈定；必须保持正常页面 Tab 顺序。右栏抽屉在窄屏关闭时仍遵循既有 `inert`。
- `draftText`、会话滚动位置、当前计划、运行状态和右栏滚动位置保存在 `appState`；打开和关闭查看态不得清空未发送草稿或重置任务。
- 高保真原型的 Markdown 仅由**手写静态 HTML fixture**模拟，不引入解析器。原始 HTML 一律禁用；未来接入动态输出时必须统一转义并以 `textContent` 或等效安全渲染写入，禁止把 Agent 输出直接交给 `innerHTML`。

## 7. 桌面交付口径与防御性折叠

### 7.1 正式口径：1200×960

阶段 4 唯一正式布局与截图验收口径是桌面 1200×960。执行侧栏或检查器按页面模式显示；对话页运行中保持 274px 外宽、242px 净宽，主区不重复实时进度。以下断点只保证既有折叠逻辑不造成信息和键盘可达性回退，不构成移动端适配承诺，也不新增正式截图交付。

### 7.2 防御性说明：979px 及以下

- 右栏沿用既有抽屉，关闭时继续使用 `inert`。
- 原“会话对象”按钮改为动态摘要：`执行中 2/4`、`等待确认`、`已暂停 2/4`、`失败 3/4`、`超时待人工`、`已阻止`或`已完成 4/4`；它保留最小任务状态，点击才打开完整步骤。
- 新会话时按钮显示“暂无执行”或隐藏；不得显示对象数造成任务已创建的误解。

### 7.3 防御性说明：759px 及以下

- 左右栏沿用既有抽屉，主标题区的动态摘要至少保留状态和步数；关闭抽屉时维持 `inert`、Escape 关闭和焦点归还。
- composer 与查看态只要求不被已有折叠逻辑遮挡、仍可滚动和键盘操作；不在本阶段承诺移动端软键盘专项优化或像素级版式。

## 8. 14 个冻结界面的布局映射

三种运行时模式：

- **E 执行侧栏：** 有长任务和连续产出，第三栏持续显示实时执行。
- **I 检查器：** 选中对象时出现上下文栏；未选中时主区扩展，窄屏用抽屉。
- **F 全宽：** 无常驻第三栏；详情按需进入抽屉或独立页。

E / I / F 不是页面的永久标签，而是业务状态驱动的布局模式。下表的“默认模式”决定首屏骨架，“进入模式”只在触发条件成立期间生效：

| 档位 | 界面 / 状态 | 默认模式 | 触发条件 | 进入模式与第三栏职责 | 退出条件 |
|---|---|---|---|---|---|
| A | 策略引擎配置 | F | 选中规则 | I：阈值、影响范围、变更摘要 | 取消选择或返回列表 → F |
| A | 实时监控看板 | F | 选中案件且无在途取证 | I：案件状态、证据摘要、人工动作 | 关闭案件 → F；开始取证 → E |
| A | 案件详情 / FR-18 取证中 | I | 调查任务进入受理、运行、暂停或失败 | E：调查轨迹的实时步骤、当前取证动作、最新证据；主区保留案件事实与处置动作 | 取证完成 → I，第三栏改为静态调查轨迹；关闭案件 → F |
| A | 模型服务 | F | 选中 Agent 或审批包 | I：当前版本、只读范围、审批状态 | 取消选择 → F |
| A | 对话窗口 | F | 首次计划进入 `awaitingConfirm`，或任务进入运行/终态 | E：确认时只给等待摘要；确认后显示实时步骤、最新产出、对象与能力事实 | 回到无任务的新会话 → F；仅查看终态对象可降为 I |
| A | 实验管理 | F | 选中静态实验 | I：配置与结果摘要 | 开始/恢复实验 → E；运行终止 → I；取消选择 → F |
| A | 实验管理 / 运行中 | I | 实验进入受理、运行、暂停或失败 | E：实验步骤、最新对比摘要、关联任务 | 完成/取消 → I |
| A | Agent 配置 | F | 选中版本或授权工具 | I：版本、授权状态、变更摘要 | 取消选择 → F |
| A | 工具台 | F | 选中工具或调用记录 | I：schema、授权、调用摘要 | 取消选择 → F |
| A | 任务队列 | F | 选中普通任务 | I：步骤快照、重试记录、错误详情 | 关闭详情 → F；进入调试执行 → E |
| A | 任务队列 / 单任务调试 | I | 发起重试、诊断或恢复且任务在运行 | E：实时步骤、当前重试、最新日志 | 调试完成/停止 → I |
| A | 证据链视图 | F | 选中证据步骤 | I：输入摘要、结果、耗时 | 取消选择 → F |
| A | 验证报告 | F | 选择既有报告 | I：门禁结果、审批对象、版本关系 | 关闭报告 → F |
| A | 验证报告 / 生成中 | F | 报告生成是持续异步任务 | E：生成步骤、最新章节、失败恢复 | 生成完成 → I；单次门禁检查为瞬时动作，只在主区或 I 中反馈，不进入 E |
| A | 日志回放 | F | 回放任务开始 | E：回放进度、当前事件、异常摘要 | 回放完成 → I；关闭记录 → F |
| A | 日志回放 / 已完成记录 | F | 选择某次已完成回放 | I：静态事件与异常详情 | 取消选择 → F |
| B | 名单管理 | F | 选中条目 | I 抽屉：条目详情 | 关闭详情 → F |
| B | 特征发布 | F | 选中发布记录 | I 抽屉：发布详情 | 关闭详情 → F |
| B | 数据集管理 | F | 选中数据集 | I 抽屉：数据集详情 | 关闭详情 → F |

案件详情中的“调查轨迹”有两种呈现：取证进行时是 E 的实时编排视图；取证完成后是 I 的只读历史。它们共用事件数据但不同时出现。验证报告的门禁检查若能同步完成，只在当前控件附近反馈，不为了瞬时动作打开执行侧栏。

B 档只登记布局归属，不扩展为可点击高保真页面。三种模式共享 260–280px 的第三栏尺寸语言，但不共享同一内容模板；同一界面必须按表中事件切换，而不是在实现时任选一个静态骨架。

## 11. 验收矩阵

测试使用确定性 fixture，并把时钟冻结为 `23:08`；不得依赖真实等待、网络或随机 ID。根节点暴露只读代理属性 `data-session-phase`、`data-run-state`、`data-workspace-mode`、`data-degraded` 供自动化观察，用户可见文案仍是验收真值。每次 transition 保存合法状态快照，断言三轴组合、对象状态和可见标签一致；这些 `data-*` 不是另一套可写状态源。

### 11.1 主路径

| 场景 | 操作 | 必须看到 | 状态断言 | 焦点断言 |
|---|---|---|---|---|
| 新会话 | 打开 `?state=empty` | 居中 textarea、3 条示例、无伪对象 | `new + idle + conversation` | textarea 获焦 |
| 空白输入 | 仅输入空格并 Enter | 不追加消息、不清空输入；出现就地提示 | 状态仍为 `new + idle` | textarea 保持焦点 |
| 首次提交 | 输入需求并 Enter | 用户消息立即出现，composer 到底部 | `active + accepting` | 焦点暂留 textarea |
| 受理中补充 | 在 1.2s 内再次提交 | 补充消息追加；只生成一份计划 | 仍为 `active + accepting`；计时器不重启 | 焦点暂留 textarea |
| 计划生成 | 冻结时钟推进 1.2s，或 demo 手动“下一步” | 助手承接 + 待确认计划 + 三个动作 | `active + awaitingConfirm` | 空 textarea 时计划标题获焦；正在输入新草稿时不抢焦点，仅播报 |
| 文本确认 | textarea 输入“确认” | 与点击确认相同 | `running`，计划折叠 | 折叠摘要获焦 |
| 非精确确认 | 输入“请确认范围” | 作为普通补充，不开始执行 | 仍为 `awaitingConfirm` | textarea 保持焦点 |
| 按钮确认 | 点击“确认执行” | 右栏出现唯一实时步骤 | `running` | 折叠摘要获焦 |
| 改参数 | 点击“改参数” | 原地参数表单 | 仍为 `awaitingConfirm` | 首字段获焦 |
| 取消计划（4C） | 点击“取消” | 计划标“已取消”，不出现 `#T-882` | `active + cancelled` | textarea 获焦 |
| 运行中追加参数 | 在 `running` 提交执行参数修改 | 后续步骤挂起；旧结果标“基于旧参数” | `awaitingConfirm` 且保存 `previousRun` | 变更计划按防抢焦点规则处理 |
| 暂停 / 继续 | 点击动作或直达 `paused` | 动态摘要和右栏同步暂停/恢复 | `paused ↔ running` | 动作后不丢失焦点 |
| 执行完成 | 完成最后一步 | `4 / 4`、报告摘要和对象均为已完成 | `active + succeeded` | 不强制移动焦点；礼貌播报完成 |
| 打开产出 | 点击“打开完整方案” | 主区显示 Markdown 效果的静态 HTML | `workspaceMode:outputViewer`，runState 不变 | 文档标题获焦 |
| 返回会话 | Escape、返回按钮、浏览器后退 | 会话草稿和滚动位置保留 | `conversation`，runState 不变 | 焦点归还触发按钮 |

### 11.2 状态与信息归属

- `empty / loading / confirm / normal / paused / completed / error / timeout / unauthorized / degraded` 十个 URL 均能直达并与 §5.5 矩阵一致。
- 同一实时步骤不得同时以展开形态出现在主区和右栏；DOM 检查只允许右栏存在当前步骤高亮和实时步数。
- 待确认计划只在主区展开；右栏不得复制四步计划。
- 错误恢复按钮只在主区；右栏不得复制操作组。
- 所有状态下，主区、动态摘要按钮、右栏对象和更新时间不得矛盾。
- `running` 主区至少存在一张 §5.1 定义的结构化结果/机制卡；移除实时进度后不得退化为只有气泡和输入框的空壳。
- 有右栏时，能力事实行必须位于其底部并使用中性辅助文字；无右栏的 `empty / loading` 按 §5.4 放在 composer 下方。“只读”“3 工具可用”不得使用 warning，未授权/待审批对象才使用对应语义色。
- 用选择器断言 `[data-live-steps]` 只在执行侧栏出现一次、`[data-capability-facts]` 位于侧栏最后一组、待确认态不存在 `[data-task-id]`；具体属性名可在实现时等价替换，但须形成稳定 DOM contract。
- 对合法状态快照逐一核对：`new` 只配 `idle`；`degraded` 只作为 flag；`outputViewer` 不改变 runState；任务对象只在确认后存在。

对 §3.4 尚未被主路径覆盖的边，增加以下 8 条确定性断言：

| # | 转移断言 | 必须核对的状态与 UI 结果 |
|---:|---|---|
| 1 | `running / paused → cancelled` | “更多任务操作 → 取消执行 → 二次确认”后不再派发步骤；迟到结果仅进入已取消任务证据，不进入结论；`degraded=false` |
| 2 | 确认运行中变更 | 从带 `previousRun` 的 `awaitingConfirm` 回到 `running`；新参数从约定步骤重跑，旧参数结果保留且不并入新结论 |
| 3 | 取消运行中变更 | 从带 `previousRun` 的 `awaitingConfirm` 回到原 `running`；原参数与当前步骤恢复，“等待变更确认”消失 |
| 4 | `failed / timedOut → running` | 对失败与超时 fixture 分别触发恢复动作；恢复点、既有结果和来源标记保留，主区与右栏同步为运行中 |
| 5 | 可选工具失败 | `runState` 保持 `running`，`data-degraded=true`；对应步骤和最新产出显式标缺失，其他步骤继续 |
| 6 | 降级解除或进入终态 | 可安全重试成功时 `data-degraded=false` 且仍为 `running`；从降级运行进入任一终态时 flag 同样清除，缺失事实只留在历史证据 |
| 7 | `blocked` 授权闭环 | 生成授权包后仍为 `blocked`、0 次未授权调用；在线批准同步后进入 `accepting` 重新预检，审批包保留且无旧执行结果被合并 |
| 8 | 终态后的两类输入 | 对 `cancelled / succeeded / failed / timedOut / blocked` 逐态参数化：执行型需求均进入 `accepting` 并新建计划，普通追问均进入 `idle` 且不创建计划；旧对象只作历史 |
