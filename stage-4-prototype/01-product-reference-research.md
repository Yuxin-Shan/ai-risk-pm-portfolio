# 阶段 4 产品参照调研

> 调研日期：2026-09-17  
> 项目属性：个人作品集；业务情境与界面数据均为虚构模拟，不代表任何真实公司实践、上线或生产指标。  
> 调研目的：提炼可用于「AI 赋能风控产品」HTML Demo 的界面模式，不复制品牌视觉，不把参照产品能力写成本项目已实现能力。

## 1. 结论先行

本项目不应做成“聊天软件套一层后台”，也不应做成只有指标卡的传统风控驾驶舱。最合适的骨架是：

- 一级左侧栏固定分成「在线风控」与「工作台」，维持 14 个冻结界面的空间心智；
- 对话窗口采用「会话流 + 结构化执行卡 + 右侧对象栏」，自然语言只是入口，计划、状态、对象和审批才是主体；
- 监控页采用「概览指标 → 趋势/状态 → 案件表 → 详情/证据」的渐进下钻；
- 任务、证据与调用记录采用时间线或 trace tree，而不是长段文字；
- 语义色只表达状态，不承担装饰：成功、警示、失败、处理中、审批中、灰度中必须可被文字再次识别。

## 2. 参照产品与可借鉴点

### 2.1 Stripe Radar：风险对象、规则与人工复核同域呈现

**官方事实**

- Radar 在 Dashboard 中组合风险评分、规则、名单、人工 review 与实时监控；规则可触发 allow、block、review 或额外认证。
- Lists 是可管理对象，列表项可按值、作者与加入日期筛选。
- Reviews 用人工判断补充自动风控；部分场景中“批准 review”与后续 capture 是两个独立动作。

**界面启发**

- 风控动作必须显式区分“系统判断”和“人确认”，不能只用一条最终状态覆盖过程。
- 规则、名单、案件、人工队列都适合使用高密度表格；详情在抽屉或独立页展开，避免主页堆满字段。
- 重要动作按钮应与状态上下文并置，例如“待人工介入”卡片中直接显示失败原因、当前管控与可执行动作。

**用于本项目**

- 在线侧采用“指标看信号、表格找样本、详情看证据、人工动作收敛状态”的四层结构。
- “确认注册 / 确认授权 / 推翻裁决”使用独立且可追溯的人工动作，不伪装成自动生效。

来源：[Stripe Radar](https://docs.stripe.com/radar)、[Radar Lists](https://docs.stripe.com/radar/lists)、[Radar Reviews](https://docs.stripe.com/api/radar/reviews)、[Review 与 Capture 分离](https://docs.stripe.com/radar/reviews/auth-and-capture)

### 2.2 Datadog：高密度监控用组件分层，而非平均铺卡片

**官方事实**

- Dashboard widget 可承载 timeseries、bar chart、table、event stream 与 monitor summary 等不同信息形态。
- Dashboard 既可作为持续更新的状态板，也可作为叙事视图；刷新频率随时间范围变化。

**界面启发**

- 指标卡只做“入口与异常信号”，趋势用图、样本用表、事件用流，不强行统一成卡片。
- 时间窗、筛选器、刷新/更新时间属于页面骨架，应固定在内容上方；系统状态不能藏在 tooltip。
- 告警色应稀缺。正常数据保持中性，只有越阈、失败和积压才使用高饱和语义色。

**用于本项目**

- 实时监控页保留 7 个指标，但用主次分组与下钻关系避免“七张同权卡片”。
- “灰度中 / 审批中 / 失败 / 待人工”均采用图标 + 文字 + 色彩三重编码。

来源：[Datadog Dashboards](https://docs.datadoghq.com/dashboards/)、[Datadog Widgets](https://docs.datadoghq.com/dashboards/widgets/)

### 2.3 LangSmith：trace tree 是证据链与日志回放的正确母型

**官方事实**

- LangSmith 的 trace tree 展示父子 run 层级，并在父子节点分别聚合用量或成本。
- CLI 与 UI 都围绕 project、trace、run、dataset、experiment、thread 等正式对象组织；run 可按错误、延迟、类型与名称筛选。

**界面启发**

- 一次 Agent 执行不应显示为“思考气泡”，而应显示为有稳定 ID、状态、时间与父子关系的执行记录。
- 证据链默认显示步骤摘要，选中某步后在相邻区域展开输入摘要、输出、耗时与错误，避免多层弹窗。
- 对话中只嵌入折叠摘要；深查时跳到独立证据链视图。

**用于本项目**

- 执行计划、任务组、证据链、报告与待注册包均成为可点击对象；右侧对象栏是会话与正式对象的桥。
- 不呈现模型隐藏推理，只呈现日志里真实存在的步骤、工具调用与结果状态。

来源：[LangSmith Cost Tracking / Trace Tree](https://docs.langchain.com/langsmith/cost-tracking)、[LangSmith CLI 对象与筛选](https://docs.langchain.com/langsmith/langsmith-cli)

### 2.4 Dify：对话、工作流画布、节点配置与运行日志各司其职

**官方事实**

- Dify Workflow 用节点画布组织 User Input、条件分支、Iteration 与 Output；节点配置在面板中完成。
- Test Run 支持按节点查看运行结果与 LAST RUN 日志；监控仪表盘用时间选择器查看消息、用户、互动深度与 token 使用趋势。

**界面启发**

- 自然语言可以发起任务，但可修改参数与运行状态应落在结构化卡片里。
- 错误应挂在具体步骤，给出恢复动作；不能只在会话末尾显示“执行失败”。
- 配置态、执行态、监控态要分开，避免一个页面承担所有操作。

**用于本项目**

- 对话主界面不嵌入完整编排画布；它展示计划与进度，配置详情仍回到 Agent 配置、实验管理、任务队列。
- 中断后保留旧参数结果，并在更新计划中指出从哪一步重跑。

来源：[Dify Workflow Quick Start](https://docs.dify.ai/en/guides/application-orchestrate/creating-an-application)、[Dify 监控仪表盘](https://docs.dify.ai/zh-hans/guides/monitoring)

### 2.5 Linear：低噪音导航、对象视图与快捷筛选

**官方事实**

- Linear 以 issue 为基础对象，并通过 workflow status、project、cycle 与 view 组织信息。
- 视图支持 list / board 切换、分组、排序、筛选与显示字段控制；团队页使用侧栏进入 Triage、Issues、Cycles、Projects 与 Views。

**界面启发**

- 侧栏只呈现稳定信息架构；筛选、排序、显示字段等临时控制放在页面工具条。
- 高密度并不等于重边框。可以靠排版层级、留白、选中态和极细分隔线维持清晰。
- 同一对象可在不同视图出现，但 ID 与状态表达应保持一致。

**用于本项目**

- 右侧对象栏统一使用对象类型、稳定编号与状态；从对话跳转后仍能识别同一对象。
- 深色版借鉴其低噪音导航和键盘工作台气质，但不复制其黑白品牌外观。

来源：[Linear Concepts](https://linear.app/docs/conceptual-model)、[Linear Display Options](https://linear.app/docs/display-options)、[Linear Team Pages](https://linear.app/docs/default-team-pages)

## 3. 横向模式归纳

| 维度 | 成熟产品共同做法 | 本项目采用 |
|---|---|---|
| 导航 | 稳定对象放侧栏，页面级筛选放工具条，详情就近展开 | 左侧两组一级导航；顶部场景与模拟数据标识；右侧对象栏 |
| 信息密度 | 指标、图、表、事件流分别承载不同任务 | 不做同质卡片墙；对话页重点是执行卡与对象 |
| 对话 + 后台 | 对话负责发起/解释，结构化控件负责确认/修改/追踪 | 会话流内嵌计划、进度、待确认、证据摘要；正式对象可跳转 |
| 状态可见 | 状态靠位置、文字、图标、颜色共同表达 | 每个异步对象都有状态标签、当前步骤、更新时间和下一动作 |
| 风险动作 | 自动判断与人工动作分层，操作后留痕 | 审批、注册、授权、推翻均突出“由人执行” |
| 下钻 | Overview → list → detail → trace | 监控指标 → 案件样本 → 案件详情 → 证据链 |

## 4. 状态色结论

| 状态 | 视觉语义 | 使用边界 |
|---|---|---|
| 成功 / 已完成 | 绿色 | 仅表示已完成且无需动作，不用于普通品牌装饰 |
| 警示 / 待确认 / 审批中 | 琥珀色 | 表示流程被人或条件挡住，必须同时显示等待对象或下一步 |
| 失败 / 已拒绝 | 红色 | 显示具体失败步骤与恢复动作，禁止只显示红点 |
| 处理中 / 执行中 | 蓝色或青色 | 配进度与当前步骤；不使用无限旋转替代真实状态 |
| 灰度中 | 蓝灰 + 斜纹或虚线 | 与“审批中”区分；必须显示范围、起止与回滚入口 |
| 暂停 / 旧参数 | 中性灰 | 保留产出并标注来源，避免误读为当前结论 |

## 5. 三层综合

- **通用基线：** 左侧导航、高密度表格、可筛选列表、详情下钻、语义状态色。
- **当前趋势：** AI 入口与传统对象管理共存；trace、run、dataset、experiment 等对象越来越显式。
- **本项目的一阶判断：** 成熟 AI 平台常为开发者假设“用户想看编排与 trace”，传统风控台又常假设“用户只想看告警与表格”。本项目的讲解对象需要同时看懂需求如何被接住、任务如何推进、结果如何受治理，因此主页面应是“对话驱动的运营控制台”，而非纯聊天或纯监控。

## 6. 明确不借鉴

- 不复制品牌配色、Logo、专有组件或页面结构；
- 不做大片渐变、玻璃拟态和满屏发光边框，避免用“AI 感”代替信息设计；
- 不把模拟数据包装成真实生产监控；
- 不把 Agent 的中间过程写成不可审计的“思维链”；
- 不因工具链能做而新增冻结总账之外的页面。
