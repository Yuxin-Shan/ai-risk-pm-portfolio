**三方共识（必须改）**
1. **需求未验证、无基线** —— Q1–Q4 全是假设且无量化；却自评 §4 全满足（Codex）。
2. **「为何需要 Agent」论证不成立** —— 「多步+工具调用」用确定性工作流+单次 LLM 调用即可；真正的论据（调查路径依赖中间结果、运行前无法预枚举、失败需自行调策略）没写（Claude）。
3. **Q3 与自设边界矛盾** —— 把「高风险处置由人直接执行」当问题，又规定「高风险一律人工确认」，问题里混入了方案预设（Claude）。
4. **场景不聚焦** —— 「商家/支付机构」「账户/商户/交易」未定；应收窄为具体场景（Codex/DSH）。
5. **用户是空壳** —— 只有角色名，缺目标/权限/痛点/成功标准；商户应与内部操作用户区分（三家）。
6. **命中红线风险** —— 既往项目指标（85%/95%/15%→0/5min）仍可能被读作「我主导过」（Claude）。
7. **缺合规与数据约束 + 基线指标**（DSH）。

## 共识修改动作（P1 V2）
1. 收窄场景为：**收单侧商户异常交易告警后的异步调查与处置**。
2. Q3 改写为「高风险处置缺少事前授权与分级确认，误操作后无法定责复盘」。
3. 新增**最小 Agent 必要性论证**：列 2–3 个「运行前无法确定调查路径」的具体场景；给「不采用 Agent 的否决条件」。
4. 问题分层：「问题是否存在」（可引行业常识，标 `[事实]`）与「影响量化」（标 `[假设]`）分开；补基线指标（before 值）。
5. 增补 5 角色表：目标/权限/痛点/成功标准；未访谈标 `[假设]`。
6. 既往指标改定性 + 标注个人角色边界；既往项目另起代号（`既往稽核项目`），与作品名区分。
7. 增补合规/数据约束：反洗钱、个人信息保护、交易数据可得性如何收窄 Agent 边界。
8. 自动动作限定为**可逆操作**（取证、建单、分派）；处置决策单独分级。
